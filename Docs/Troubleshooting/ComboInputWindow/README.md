# 콤보 입력 구간 분리와 저프레임 입력 검증

기록일: 2026-10-31 · 프로젝트: BladeZ · 엔진: UE 5.6

결론 정리: 2026-11-01 · 관찰 결과와 현재 구현 범위에 맞춰 미해결 문제로 오해될 표현을 수정했다.

선행 기록: [10 FPS 콤보 전환 실패와 몽타주 Blend Out](../ComboBlendOut/README.md)

상태: 사용자가 Notify State 입력 윈도우를 구현하고 콤보 연결을 확인했다. 제공된 로그에서도 구간 안 입력 뒤 소비·전환 경로가 실행되는 것을 확인했다. 이번 입력 윈도우 관찰에서 저장된 입력의 소실이나 소비 후 점프 실패 사례는 없었다. 논의 대상은 구간 밖에 도착한 입력에 대한 추가 보정이었으며, 게임의 요구사항과 구현 비용을 비교해 유효한 최신 입력 하나를 보관·소비하는 구조를 유지하기로 했다(11절). 별도 입력 스레드와 다중 입력 이력 수집은 이번 구현 범위에서 제외한다.

자료는 대화에서 사용자가 설명한 재현 결과, 직접 붙여 넣은 로그, GitHub 커밋, 기록 시점의 로컬 코드다. 아래에서 코드로 확인한 사실과 사용자 보고, 아직 검증하지 않은 가설을 구분한다. 사용자가 구현하고 함께 설계·검토하는 방식으로 진행했다. 이번 기록 작업은 문서만 변경하며 별도의 실행 검증을 의미하지 않는다.

## 1. 해결하려는 문제

기존 시스템은 공격 중이면 최신 입력 하나를 저장하고 콤보 체크 Notify에서 소비했다. 그 결과 3타 초반에 연타한 클릭이 다음 공격 입력으로 남아, 사용자가 3타에서 멈추고 싶어도 4타로 이어지는 문제가 있었다.

목표는 다음과 같다.

1. 공격 모션별로 지정한 구간에서만 다음 입력을 받는다.
2. 입력 구간이 끝나도 저장된 입력은 유지하고, 원하는 전환 시점에서 소비한다.
3. 스타일리쉬한 공격을 위한 기본 Play Rate 2.5를 유지하면서 빠른 속도와 긴 블렌드 아웃에서도 연결·종료를 검증한다.

위 항목은 설계 당시의 목표다. 이후 확인한 입력 소비·콤보 연결 결과와 추가 보정의 도입 여부는 9~11절에 정리했다.

## 2. 이전 Notify State 시스템을 다시 확인한 이유

사용자는 이전 시스템에서도 입력 윈도우를 사용했지만, 빠른 재생 속도와 블렌드 아웃 조건에서 콤보가 이어지지 않아 현재의 공격 전 구간 입력 방식으로 바꿨다고 설명했다.

추가 사용자 보고:

- 이전 코드로 2.0배속까지 확인했지만 연결되지 않아, 당시에는 1.0~1.5배로 낮춰 두었다.
- 블렌드 아웃을 끄자 2.0배 이상에서도 몽타주 점프가 가능해지기 시작했다.
- 따라서 커밋에 남은 낮은 재생 속도는 최종적인 공격 감각 목표가 아니라 당시의 대응이었다.

이 보고는 자동 블렌드 아웃과 전환 실패의 연관성을 뒷받침한다. 다만 당시의 전체 설정·실행 로그가 없으므로 특정 실패의 내부 호출 순서를 확정하지 않는다. 사용자가 말한 블렌드 아웃 해제의 정확한 설정값도 이 대화의 로그에 포함되어 있지 않다.

이전 State의 End는 입력 허용 플래그만 닫았으며, 배열은 `OnAttackEnded()`에서 비웠다. 따라서 해당 코드에 대해 “State 종료가 입력을 먼저 지워서 실패했다”고 설명하면 안 된다.

이전 `CheckCombo()`는 점프 요청 후 실제 적용 여부와 무관하게 현재 콤보 이름과 입력 인덱스를 진행했다. 입력이 저장돼 있어도, End 시점에 몽타주가 이미 비활성 상태라면 점프만 적용되지 않을 수 있는 경로였다. 이는 코드상 가능한 실패 경로이며, 이전 모든 실패의 확정 원인은 아니다.

## 3. 설계 논의와 선택

검토한 방식은 두 가지다.

| 방식 | 입력 구간 종료 | 소비·전환 지점 |
| --- | --- | --- |
| 입력 유지 | 새 입력만 차단하고 Left/Right 유지 | 다음 노드를 결정하고 점프·입력 정리 |
| 다음 공격 예약 | 입력을 해석해 다음 노드를 예약 | 예약된 노드로 점프·예약 정리 |

1차 구현은 **입력 유지 방식**을 선택했다. 기존 입력 슬롯과 콤보 체크 Notify를 활용하면서 입력 수락 조건만 분리할 수 있기 때문이다. 다음 노드 사전 예약은 현재 요구에 필수적이지 않다고 판단했다.

```text
공격 시작
  → 입력 불가
  → Notify State Begin: 입력 허용
  → 구간 안의 클릭: 최신 입력 하나 저장
  → Notify State End: 추가 입력 차단, 저장된 입력 유지
  → 기존 콤보 체크 Notify: 입력 해석·전환 요청·입력 소비
  → 공격 종료: 공격 상태·입력·윈도우 초기화
```

입력 구간과 소비 지점은 공격 모션별로 따로 배치한다. 입력 구간 종료 자체가 점프나 버퍼 폐기 명령은 아니다.

## 5. 애니메이션 프레임과 게임 프레임을 구분

먼저 “입력 가능 구간이 애니메이션상 10프레임이면 짧은가?”를 논의했다. 일정 2.5배속, 시간 배율 변경이 없다는 가정에서는 다음과 같다.

| 애니메이션 시간 기준 | 원래 10프레임 길이 | 2.5배속에서의 이론적 길이 |
| --- | --- | --- |
| 30 FPS | 약 333ms | 약 133ms |
| 60 FPS | 약 167ms | 약 67ms |

```text
이론적 시간 = 애니메이션 프레임 수 / 애니메이션 FPS / 일정 Play Rate
```

당시 타임라인 FPS가 확정되지 않았으므로 현재 에셋이 위 표 중 어느 조건인지는 단정하지 않는다. 이 표를 이후 `GFrameCounter` 로그의 시간 환산에 그대로 적용하면 안 된다.

## 6. 10 FPS 입력 저장·전환 요청 로그

출처: [01-10fps-input-and-jump.txt](evidence/01-10fps-input-and-jump.txt). 사용자가 채팅에 직접 제공한 발췌를 보관했다. 전체 실행 로그가 아니다.

`t.MaxFPS 10`에서 좌클릭을 연타했고, `NextInputType set to: 0`과 `L_1 → LL_2 → LLL_3 → LLLL_4` 등의 전환 요청이 기록됐다. 사용자는 이 실행에서 입력이 들어가지 않는 것 같다고 보고했다.

로그 해석의 한계:

- `NextInputType set`은 `SetAttackInput()`의 조건 검사 뒤에 있으므로 **수신한 모든 입력이 아니라 수락·저장한 입력만** 보여준다.
- 같은 구간에서 여러 번 저장하면 최신 값으로 덮어쓴다. 입력 로그 개수를 실제 진행한 공격 수로 읽지 않는다.
- `Jumping to section`은 점프 호출 전에 찍는 **요청 로그**다. 실제 섹션 변경 성공을 보증하지 않는다.
- 이 발췌에는 입력 거절, 빈 버퍼로 인한 소비 생략, 시작·종료, 재생 인스턴스 식별 정보가 없다. 중간에 `L_1`이 다시 등장한 이유를 이 로그만으로 확정하지 않는다.

이 초기 발췌만으로는 콤보가 이어지지 않은 구간에 입력이 언제 도착했는지 구분하기 어려웠다. 이후 입력과 윈도우의 프레임 로그를 함께 비교해 구간 내·외 입력을 구분했다(10절).

## 7. BEGIN/END 게임 프레임 측정과 10·60 FPS 비교

실제 경과 시간 저장 변수를 추가하는 대신, 사용자 요청에 따라 State Begin/End에 `GFrameCounter` 로그를 넣는 방식으로 먼저 관찰했다.

```cpp
UE_LOG(LogTemp, Log, TEXT("Window BEGIN | Frame=%llu"),
    static_cast<unsigned long long>(GFrameCounter));

UE_LOG(LogTemp, Log, TEXT("Window END | Frame=%llu"),
    static_cast<unsigned long long>(GFrameCounter));
```

출처: [02-10fps-window-frames.txt](evidence/02-10fps-window-frames.txt), [03-60fps-window-frames.txt](evidence/03-60fps-window-frames.txt)

| FPS 조건 | BEGIN | END | 게임 프레임 차이 | 설정 FPS대로 일정하게 실행됐다고 가정한 시간 |
| --- | ---: | ---: | ---: | ---: |
| 10 FPS 제한, 사용자 보고 | 50663 | 50665 | 2 | 약 200ms |
| 10 FPS 제한, 사용자 보고 | 50690 | 50692 | 2 | 약 200ms |
| 10 FPS 제한, 사용자 보고 | 50706 | 50708 | 2 | 약 200ms |
| `t.MaxFPS 60` | 52275 | 52287 | 12 | 약 200ms |
| `t.MaxFPS 60` | 52433 | 52445 | 12 | 약 200ms |
| `t.MaxFPS 60` | 52574 | 52586 | 12 | 약 200ms |

```text
10 FPS: 2 / 10 = 0.2초
60 FPS: 12 / 60 = 0.2초
```

해석:

1. 제공된 세 쌍씩의 로그에서는 BEGIN과 END가 같은 게임 프레임에 발생하지 않았다.
2. 두 조건 모두 추정 지속 시간은 약 200ms다. **이번 샘플은 저프레임 때문에 윈도우의 실제 시간이 줄었다는 근거가 아니다.**
3. 같은 추정 시간 동안 진행한 게임 프레임 수가 12에서 2로 줄었다. 입력 처리와 애니메이션 업데이트의 시간 해상도 차이를 조사할 단서지만, 이것만으로 입력 누락 원인을 확정하지 않는다.
4. 게임 프레임 차이로 환산한 시간이므로 Play Rate 2.5로 다시 나누지 않는다.
5. `t.MaxFPS`는 상한 설정이다. 실제 FPS와 프레임 간격이 기록되지 않아 200ms는 측정된 벽시계 시간이 아니라 근삿값이다. 프레임 내부의 콜백 실행 위치도 반영하지 못한다.
6. 약 200ms가 열려 있어도 연타 클릭이 반드시 들어온다는 보장은 없다. 각 클릭의 수신 시점과 윈도우의 실제 활성 상태를 함께 봐야 한다.
7. 현재 BEGIN/END 로그는 객체 유효성 검사와 플래그 변경 **앞**에 있다. 미리보기처럼 콜백 진입 후 조기 반환한 경우에도 출력될 수 있다. 따라서 현 로그는 콜백 진입 기록이며 실제 입력 플래그 변경까지 증명하지 않는다. 액터·메시·섹션 식별 정보도 없어 여러 대상이 섞였다면 짝을 다시 확인해야 한다.

### 조사 중 검토했으나 이번 로그에서 관찰되지 않은 가설

빠른 재생과 긴 프레임 간격에서 한 애니메이션 업데이트가 짧은 구간 전체를 지나갈 수 있다. Branching Point가 Begin/End를 처리하더라도 그 사이에 입력 콜백이 실행되지 않으면 bool 기반 입력 조건을 통과할 기회가 없을 수 있다.

이는 가능한 실패 모델로 논의한 것이다. **이번 10 FPS의 50663–50665 등 세 쌍은 같은 프레임 종료가 아니므로 이 가설을 재현한 증거로 쓰지 않는다.** Branching Point는 몽타주 이벤트 처리 위치·순서를 제어하며, 프레임 사이에 입력 처리를 추가해 주는 것은 아니다.

## 8. 초기 조사에서 검토한 계측 방법

아래는 입력과 윈도우의 순서를 확인하기 전에 검토한 진단 방법이다. 현재 남은 문제나 필수 후속 작업 목록이 아니다. 실제로는 입력 전달 직전의 Frame 로그를 추가했고, 구간 안 입력 뒤 소비·전환 경로가 실행되는 결과와 구간 밖에 입력이 도착하는 사례를 구분했다(10절).

| 지점 | 필요한 정보 | 확인할 질문 |
| --- | --- | --- |
| 입력 콜백 또는 `SetAttackInput()` 진입, 조건 검사 전 | Frame, Input, Window, Attacking, 액터 | 입력이 도착했는가? 어느 조건 때문에 거절됐는가? |
| State의 실제 플래그 변경 시점 | Frame, Open/Close, 액터, 몽타주·섹션 | 로그뿐 아니라 실제 구간이 열렸는가? 입력 전후 어느 순서였는가? |
| `CheckCombo()`의 입력 유무 검사 전 | Frame, HasInput, Window, 현재 노드 | 소비 시 버퍼가 비어 있었는가? |
| 점프 전후 | 인스턴스 ID, 활성·정지 상태, 요청 섹션과 실제 섹션 | 요청이 실제로 적용됐는가? |

경계 프레임에서는 프레임 번호만으로 선후를 알 수 없으므로 로그 순서도 같이 본다. 서로 다른 실행의 프레임 번호를 연결하지 않는다.

당시 검토한 조건별 진단 기준:

- 입력 진입 로그 없음: 캐릭터 입력 콜백과 그 이전 전달 경로 확인.
- 입력 진입은 있지만 Window=false: 윈도우 배치·실행 순서에 의한 거절 확인.
- 소비 시 HasInput=false: 입력 수락부터 버퍼 유지까지 확인.
- 소비 시 HasInput=true인데 실제 점프 실패: 몽타주 활성 상태·블렌드 아웃 조사.

당시 검토한 재현 항목:

- 구간 전에만 연타하고 멈추면 다음 공격을 예약하지 않는가?
- 구간 안에서 한 번 누르고 손을 떼도 구간 종료 후 소비되는가?
- 10·60 FPS에서 입력 수신·구간 변경·소비 로그를 같은 실행 안에서 수집할 수 있는가?
- 입력을 저장한 뒤 피격·대시로 중단하면 다음 공격으로 새지 않는가?
- Play Rate, AttackRate 커브, HitStop, Blend Out Time, Trigger Time, Auto Blend Out 설정을 함께 기록했는가?
- 입력 없는 공격의 정상 종료와 이동 복귀가 되는가?

## 9. 현재 결론과 재사용할 검증 원칙

- 입력 구간과 소비 지점을 분리하는 1차 구조는 사용자가 구현했다.
- State 종료는 새 입력만 막고 저장된 입력은 유지한다.
- 과거의 블렌드 아웃 관련 전환 실패 기록과 이번 입력 윈도우 관찰을 구분한다.
- 10 FPS에서 2프레임, 60 FPS에서 12프레임이라는 콜백 간격을 각각 세 번 관찰했다. 일정 FPS 가정에서는 모두 약 200ms다.
- 후속 로그에서 구간 안 입력 뒤 소비·전환 경로가 실행되는 것을 확인했고, 사용자는 실제 콤보 연결을 확인했다(10절). 이번 관찰에서 저장된 입력의 소실이나 소비 후 점프 실패 사례는 없었다.
- 구간 밖에 도착한 입력에 대한 보정 대안을 검토했으며, 게임의 요구사항과 구현 비용을 고려해 추가하지 않기로 했다(11절).
- 최소 계측으로 시작하되 수신·수락·소비·적용을 분리해서 읽는다. 로그 위치가 조건 검사 전인지 후인지도 기록한다.
- 관찰값과 추정값을 구분한다. 게임 프레임 차이와 애니메이션 프레임 수는 서로 다른 시간 기준이다.
- 관찰되지 않은 실패 가능성을 현재 미해결 문제로 기록하지 않는다. 과거 진단 가설과 현재 확인한 결과도 구분한다.

## 10. 후속 관찰: 입력 콜백과 윈도우 시점의 불일치

출처: [04-input-window-order.txt](evidence/04-input-window-order.txt). 사용자가 좌클릭 프레임 로그를 추가한 뒤 제공한 발췌다. 이 발췌 자체에는 FPS 명령과 실제 프레임 시간이 없으므로, 시간을 계산할 때에는 10 FPS 유지 여부를 별도로 확인해야 한다.

코드에서 `Left Input`의 위치를 확인했다. `PlayerLeftAttack()`에서 무기·컴포넌트·접지 등의 조건을 통과하고, 새 공격 시작 분기를 지난 뒤, `SetAttackInput(Left)`를 호출하기 직전에 출력한다. 따라서 **공격 중 후속 입력을 전투 컴포넌트로 전달하려 한 기록**이다. 모든 물리 클릭이나 공격을 시작한 첫 클릭을 기록하지는 않는다.

| 구간 | 로그 순서 | 해석 |
| --- | --- | --- |
| 62472–62474 | Left 62472 → BEGIN 62472 → END 62474 → Left 62477 | 첫 입력은 같은 프레임이어도 BEGIN보다 앞이다. BEGIN과 END 사이에 후속 입력 로그가 없다. |
| 62515–62517 | Left 62514 → BEGIN 62515 → END 62517 → 다음 Left 62528 | 입력이 구간 전후에 있고 구간 내부에는 없다. |
| 62549–62551 | Left 62548 → BEGIN 62549 → END 62551 → Left 62553 | 같은 패턴으로 구간 내 입력 기회가 비어 있다. |
| 62509–62511 | BEGIN 62509 → Left 62511 → END 62511 → LL_2 전환 요청 | END와 같은 프레임이어도 그보다 먼저 도착한 입력 뒤에 전환 요청이 관찰된다. |
| 62566–62568 | BEGIN 62566 → Left 62567 → END 62568 → Left 62569 → LLL_3 전환 요청 | 구간 내 입력을 유지하고 나중에 소비하는 구조와 일치한다. 62569 입력이 전환 원인이라고 읽지 않는다. |
| 62636–62638 | BEGIN 62636 → END 62638 | 발췌 내 이 구간에는 Left Input 로그가 없다. |

판단:

- 클릭 콜백이 전혀 오지 않는다는 설명보다 **입력 전달 시점과 허용 구간이 엇갈린다**는 설명을 지지한다.
- 대상이 동일하고 BEGIN의 유효성 검사를 통과했으며, 이전 구간이 정상 종료했다는 전제에서 BEGIN 전·END 후 입력은 현재 bool 조건에서 거절된다. 구간 내부 입력 뒤에는 전환 요청이 여러 차례 기록됐다.
- 이는 엄격한 구간 제한이 의도대로 입력을 거절한 결과일 수 있다. 시스템이 수신한 입력을 무작위로 잃었다고 표현하지 않는다.
- 이번 발췌 역시 윈도우를 같은 프레임에 열고 닫은 사례를 보여주지 않는다. 앞서 제시한 같은 프레임 가설을 원인으로 확정하지 않는다.
- 프레임 번호가 같아도 로그 순서가 중요하다. `Left → BEGIN`과 `Left → END`는 허용 여부가 다를 수 있다.
- 구간 종료 후 입력을 유지한다는 정책과 관찰은 일치하지만, 소비 로그에 버퍼의 입력 프레임이 없으므로 개별 입력과 소비의 연결은 코드와 순서에 근거한 해석이다.
- 구간 안 입력 뒤 소비·전환 경로가 실행되는 로그와 사용자의 실제 콤보 연결 확인을 함께 현재 결과로 기록한다. 이번 관찰에는 저장된 입력의 소실이나 소비 후 점프 실패 사례가 없었다.

이 관찰 이후 입력 구간 밖의 클릭을 보정할지와 입력 수집 방식을 논의했다. 구간 배치·길이 조정과 시작 직전 입력 유예는 서로 다른 정책이며, 별도의 유예는 채택하지 않았다. 원래의 “공격 초반 연타로 다음 공격을 미리 예약하지 않는다”는 목표를 유지하면서 내린 결정은 다음과 같다.

## 11. 입력 지연 보강 대안과 구현 범위 결정

### 확인한 결과와 추가 보정의 논의 대상

확인한 범위에서는 입력 가능 구간 안에 들어온 입력이 소비되어 콤보 연결로 이어졌다. 로그로 소비·전환 경로의 실행을 확인했고, 사용자가 실제 연결도 확인했다. 추가 보강 논의는 구간 밖에 도착한 입력을 보정해서 받아줄지에 관한 것이었다. 물리적인 클릭 시점과 게임 로직 도착 시점 사이의 지연은 측정하지 않았으므로, 구간 밖 도착의 원인을 모두 전달 지연으로 단정하지 않는다.

`PlayerLeftAttack()`에서 기록한 시각은 게임 로직의 콜백 처리 시각이다. Windows 메시지 생성 시각도 실제 마우스 스위치가 눌린 물리 시각과는 구분해야 한다. 더 앞선 시각을 확보하려면 입력 수집 경로를 계측하고, 입력과 애니메이션 구간을 비교할 시간 기준을 맞춰야 한다.

### 검토한 대안과 트레이드오프

| 대안 | 기대 효과 | 비용·한계 및 이번 판단 |
| --- | --- | --- |
| 큐·배열에 입력 종류와 시각을 보관 | 여러 입력 이력을 유지하고 나중에 유효 구간에 속한 입력을 선택할 수 있다. | 콜백 도착 시각만 저장하면 전달 이전의 지연을 복원하지 못한다. 소비·폐기·공격 간 이월 규칙도 필요하다. 현재는 유효한 최신 입력 하나만 필요하므로 도입하지 않는다. |
| 입력 수집을 별도 스레드로 분리 | 게임 스레드의 업데이트 사이에도 입력을 수집할 수 있다. | 수집 경로 변경, 스레드 간 전달·동기화, 입력 시각과 애니메이션 구간의 대응이 필요하다. 가져오는 순간의 윈도우 bool만 검사하면 수집 시각을 활용하지 못한다. 게임 로직과 화면 반응의 프레임 지연까지 없어지는 것도 아니다. 이번 범위에서 제외한다. |
| 입력 수락에 50ms 간격 제한 | 짧은 간격으로 반복되는 입력의 저장·후속 처리 횟수를 제한한다. | 입력 콜백 호출 자체나 전달 지연을 줄이지 못한다. 좌클릭 후 30ms에 들어온 우클릭도 거절할 수 있어, 실제 최신 입력이 아니라 제한을 통과한 최신 입력을 소비하게 된다. 별도 필요성이 확인되지 않아 채택하지 않는다. |
| 최신 입력 단일 슬롯 유지 | 현재 소비 규칙을 직접 표현하며 입력 수락과 소비 시점을 분리할 수 있다. | 과거 입력 이력에 기반한 보정은 제공하지 않는다. 현재 게임의 요구에 맞는 선택으로 유지한다. |

별도 스레드 기반 입력 수집은 실제 가능한 접근이다. 예를 들어 [Microsoft GameInput의 입력 콜백](https://learn.microsoft.com/en-us/gaming/gdk/docs/features/common/input/advanced/input-callbacks)은 내부 작업 스레드에서 전달된다. 이는 대안의 근거이며, 현재 프로젝트에 해당 경로를 구현하거나 적용 효과를 검증했다는 뜻은 아니다. 언리얼 객체와 게임 상태를 다른 스레드에서 직접 조작하는 방식으로 단순 전환하지 않으며, 스레드 간 데이터 전달과 소유권을 고려해야 한다([Epic의 스레드 간 객체 접근 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine)).

### 선택 기준과 최종 방향

사용자는 현재 게임이 매우 정밀한 입력 타이밍을 핵심 요구로 삼는 게임은 아니라고 판단했다. 따라서 극단적인 저프레임에서도 입력 시각을 복원하는 복잡도를 도입하기보다, **입력 가능 구간에서 받은 유효한 최신 입력을 안정적으로 소비하는 것**을 우선한다.

이는 버퍼링 자체를 배제하는 결정이 아니다. 현재의 `NextInputType + bHasNextInput`도 입력 하나를 저장했다가 나중에 소비하는 단일 슬롯 버퍼다. 이번에 추가하지 않기로 한 것은 큐·배열을 통한 다중 입력 이력 수집과 별도 입력 스레드다.

유지하기로 한 입력 정책은 다음과 같다.

1. 공격 중이며 입력 가능 구간이 열려 있을 때 받은 최신 입력 하나를 저장한다.
2. 입력 구간이 닫혀도 저장된 입력은 유지하고, 지정된 소비 시점에서 처리한다.
3. 소비·공격 종료·중단 시 입력이 다음 공격으로 잘못 이월되지 않도록 상태를 정리한다.

**구간 안 입력의 소비와 콤보 연결을 확인한 현재 구조를 유지하고, 구간 밖에 도착한 입력을 되살리는 시간 보정은 도입하지 않는다.** 이는 관찰된 저장·소비 실패를 미해결로 남긴 결정이 아니라, 추가 보정의 필요성과 구현 비용을 비교해 범위를 정한 결정이다.

### 트레이스와 입력의 보강 수준을 다르게 정한 이유

보강 수준은 각 시스템이 의도한 전투 경험에 미치는 영향과 구현·검증 비용을 기준으로 정했다. 사용자는 다수의 적을 공격하는 상황에서 저프레임으로 인해 공격 궤적 안의 적이 타격 판정에서 누락되는 것은 게임의 의도에 어긋난다고 판단했다. 따라서 트레이스는 프레임 사이의 공격 궤적을 충분히 검사해 의도한 타격 결과를 반영하는 방향으로 보강했다.

입력 역시 유효하게 받은 공격 의도를 정상적으로 반영해야 한다. 다만 현재 게임은 매우 정밀한 입력 타이밍을 핵심 요구로 삼지 않으므로, 별도 입력 스레드와 타임스탬프 기반 보정까지 도입하는 것은 기대 효과 대비 구현·검증 비용이 크다고 판단했다. 입력 가능 구간에서 받은 최신 입력을 유지하고, 지정된 소비 시점에 처리하는 범위를 우선한다.

| 시스템 | 우선 보장하려는 동작 | 보강 범위를 정한 이유 |
| --- | --- | --- |
| 공격 트레이스 | 공격 궤적 안의 적에 대한 타격 판정 | 다수의 적을 공격할 때 프레임 간격으로 판정이 누락되면 의도한 공격 결과가 달라지므로, 궤적 검사 보강을 우선했다. |
| 콤보 입력 | 입력 가능 구간에서 받은 최신 입력의 유지·소비·전환 | 현재 게임이 요구하는 타이밍 정밀도에 맞춰 단일 슬롯 구조를 유지한다. 게임 로직 도착 전의 입력 시각을 복원하는 추가 보정은 이번 범위에서 제외했다. |

핵심은 **트레이스는 의도한 타격 결과를 반영하는 데 집중하고, 입력은 유효하게 받은 공격 의도를 안정적으로 반영하는 범위로 보강했다**는 것이다. 플레이 경험에 필요한 보장 수준과 개발 비용을 비교해 우선순위를 정한 결정이다.

이 절은 사용자가 설명한 트레이스 보강 목적과 이번 입력 설계 판단을 함께 기록한 것이다. 트레이스 구현을 이번 문서 작업에서 다시 검토하거나, 모든 저프레임 조건에서 타격 누락이 없음을 새로 검증한 것은 아니다.

### 후속 논의: 동일 입력의 중복 갱신

이미 같은 입력이 보관 중이면 갱신을 건너뛰는 방법도 논의했다. 이 경우 조건은 `bHasNextInput && NextInputType == NewInputType`이어야 한다. 입력값만 비교하면 이전 입력을 소비한 뒤에도 남아 있는 값 때문에 새로운 동일 입력까지 거절할 수 있다.

이는 중복 갱신을 생략한다는 의도 표현이며, 성능 개선을 검증한 결과가 아니다. enum·bool 할당은 저렴하고 비교·분기도 비용이 있으므로 최적화 효과를 보장하지 않는다. 이번 문서 정리에서 해당 코드 변경은 수행하지 않았다.

이번 결정은 논의를 통해 정한 구현 범위다. 새로운 런타임 계측이나 플레이 검증을 추가로 수행한 결과는 아니다.
